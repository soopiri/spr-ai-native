LLM의 흔한 코딩 실수를 줄이기 위한 행동 지침입니다.

### 1. 코딩 전에 먼저 생각하세요

**가정하지 마세요. 혼란을 숨기지 마세요. 트레이드오프를 드러내세요.**

구현하기 전에:
- 당신의 가정을 명시적으로 진술하세요. 확신이 없다면 질문하세요.
- 여러 가지 해석이 가능하다면, 묵묵히 선택하지 말고 모두 제시하세요.
- 더 단순한 방법이 있다면 말하세요. 필요할 때는 반박하세요.
- 불분명한 부분이 있다면 멈추세요. 무엇이 혼란스러운지 말하고, 질문하세요.

### 2. 단순함이 먼저입니다

**문제를 해결하는 최소한의 코드만 작성하세요. 추측성 코드는 일절 포함하지 마세요.**

- 요청받지 않은 기능은 만들지 마세요 (오버 엔지니어링 금지).
- 일회성 코드에는 추상화가 필요 없습니다.
- 요청되지 않은 "유연성"이나 "구성 가능성"은 만들지 마세요.
- 일어날 수 없는 시나리오에 대한 에러 처리는 하지 마세요.
- 200줄을 작성했는데 50줄로도 가능하다면 다시 작성하세요.

스스로에게 물어보세요: "시니어 엔지니어가 이걸 보고 과하다고 말할까?" 그렇다면 단순화하세요.

### 3. 수술하듯 고치세요

**꼭 필요한 부분만 건드리세요. 본인이 만든 잔해만 치우세요.**

기존 코드를 수정할 때:
- 인접한 코드, 주석, 포맷팅을 "개선"하지 마세요.
- 멀쩡한 것을 굳이 리팩터링하지 마세요.
- 당신의 방식과 다르더라도 기존 스타일을 따르세요.
- 관련 없는 사용되지 않는 코드(dead code)를 발견하면 삭제하지 말고 언급해주세요.

당신의 변경으로 고아(orphan) 파일이 생긴 경우:
- 당신의 변경으로 인해 사용되지 않게 된 import/변수/함수는 제거하세요.
- 요청받지 않았다면 기존부터 있던 죽은 코드는 제거하지 마세요.

테스트: 변경된 모든 줄은 사용자 요청과 직접 연결되어야 합니다.

### 4. 목표 기반 실행

**성공 기준을 정의하고 검증될 때까지 반복하세요.**

작업을 검증 가능한 목표로 변환하세요:
- "유효성 검증 추가" → "유효하지 않은 입력에 대한 테스트를 작성하고, 통과하게 만들기"
- "버그 수정" → "버그를 재현하는 테스트를 작성하고, 통과하게 만들기"
- "리팩터링 X" → "리팩터링 전후 모두 테스트가 통과하는지 확인하기"

여러 단계의 작업은 간단한 계획을 세우세요:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

명확한 성공 기준은 독립적인 반복 작업을 가능하게 합니다. 반면, 모호한 기준("그냥 작동하게 하라")은 지속적인 명확화를 요구합니다.
