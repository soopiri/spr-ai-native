## 4. 검증 항목

engineer는 구현 후, qa는 검증 시 아래 항목을 수행합니다. **명령 칸은 비워둬도 됩니다.** 비어 있으면 에이전트가 프로젝트 설정에서 실제 명령을 찾아 실행하고, 찾은 명령을 이 표에 적어 넣습니다.

| 항목 | 실행 | 명령 |
|---|---|---|
| 린트 | 필수 | |
| 타입 체크 | 필수 | |
| 단위 테스트 | 필수 | |
| 통합 테스트 | 선택 | |
| 빌드 | 선택 | |
| 포맷 검사 | 안 함 | |
| 단일 테스트 실행 | — | |

**`실행` 값**

| 값 | 의미 |
|---|---|
| `필수` | 실행하고, 실패하면 FAIL |
| `선택` | 실행하되 실패는 보고만 (판정에 반영하지 않음) |
| `안 함` | 실행하지 않음. 이 프로젝트에 해당 없음 |

`단일 테스트 실행`은 판정 항목이 아니라 engineer가 반복 실행에 쓰는 명령입니다.

### 명령을 찾는 방법

명령 칸이 비어 있으면 아래 순서로 **근거를 찾아** 채웁니다.

1. 패키지 매니페스트 · 태스크 러너에 정의된 스크립트
2. CI 설정이 실행하는 명령
3. 해당 도구의 설정 파일이 있으면, 그 도구의 표준 실행 방법

**찾은 명령은 이 표에 적어 넣습니다.** 다음 회차부터는 다시 찾지 않습니다.

### 찾을 때 지켜야 할 것

- **근거가 없으면 실행하지 않습니다.** "아마 이 명령일 것"은 발견이 아니라 추측입니다. 근거를 못 찾으면 **N/A**로 보고하고 사용자에게 표 갱신을 요청하세요.
- **끝나지 않는 명령(감시 모드)을 그대로 쓰지 마세요.** 1회 실행 옵션을 확인하고, 없으면 N/A로 보고합니다.
- **코드를 자동 수정하는 옵션이 붙은 명령을 쓰지 마세요.** 검사만 하는 형태를 찾고, 없으면 N/A로 보고합니다. qa는 코드 수정이 금지되어 있습니다.
- 외부 서비스 · 자격증명이 없어 실패한 경우는 FAIL이 아니라 **N/A(환경 미비)** 로 보고합니다.
- 어디서 찾았는지(파일 · 위치)를 보고에 남깁니다.

## 5. 산출물 · 워크플로우 규약

모든 작업 산출물은 `works/<task_id>/` 아래에 기록합니다.

| 파일 | 작성자 | 갱신 방식 |
|---|---|---|
| `pm-brief.md` | pm (착수 시, 사용자 확인 대상) | 덮어쓰기 |
| `pending.md` | planner (Phase 1) | 덮어쓰기 |
| `plan.md` | planner (Phase 2) | 덮어쓰기 |
| `decisions.md` | planner (Phase 2) | 덮어쓰기 |
| `engineer.md` | engineer | 회차별 append |
| `qa.md` | qa | 회차마다 덮어쓰기 |
| `followups.md` | planner 최초 작성, engineer·qa append | append only |
| `pm-report.md` | pm (완료 시) | 덮어쓰기 |

`works/` 밖에서 에이전트가 쓰는 파일은 아래 하나뿐입니다.

| 파일 | 작성자 | 갱신 방식 |
|---|---|---|
| `README.md` | engineer(실행 방법) → pm(개요 · 범위 · 알려진 한계) | 해당 섹션만 갱신 |

- README는 **사용자에게 보이는 변화가 있을 때만** 갱신합니다. 내부 리팩터링·테스트 추가만으로는 건드리지 않습니다.
- `works/`를 git에 커밋할지: <커밋함 / 커밋하지 않음(.gitignore에 추가)>

### 작업 예산

pm이 워크플로우를 시작하기 전에 읽습니다. **아래는 기본값입니다.** 작업 규모·마감·리스크에 맞게 조정하세요. 표가 없으면 에이전트는 기본값으로 동작합니다.

| 항목 | 값 |
|---|---|
| QA fix 재시도 횟수 | 3 |
| 계획 단계 | 분리 |

- **QA fix 재시도 횟수** — QA가 FAIL / PARTIAL일 때 engineer를 재호출하는 최대 횟수입니다. 소진하면 pm은 임의로 통과시키지 않고 `미완료(에스컬레이션)`으로 보고합니다. `0`이면 fix 없이 첫 QA 결과로 종료합니다.
- **계획 단계** — planner를 몇 번 호출할지 결정합니다.
  - `분리` — Phase 1(미결정 분석) → 사용자 결정 → Phase 2(계획 수립). 호출 2회, 정지 1회.
  - `통합` — planner가 `pending.md`와 **권장안을 채택했다고 가정한 계획서**를 한 번에 작성합니다. 호출 1회, 정지 0~1회. 사용자가 권장안과 다르게 결정하면 Phase 2를 다시 호출해야 하므로 그만큼 계획 작성이 헛일이 됩니다. **결정이 뒤집힐 가능성이 낮거나 시간이 촉박할 때** 쓰세요.
